# Gladiator HTML

Web-прототип игры про гладиаторскую школу с читаемым, полностью детерминированным боем. Игрок ведёт школу через **сезон из трёх серий**: на экране сезона выбирает следующую серию, в каждой серии распределяет доступных гладиаторов — каждый используется в серии не более одного раза — по трём видимым противникам, смотрит бои на процедурно анимированной 3D-арене и по завершении серии возвращается на экран сезона, пока не сыграны все три.

Правило контр-треугольника всегда на экране: **Murmillo → Retiarius → Hoplomachus → Murmillo**, где стрелка означает «имеет типовое преимущество против». Это **собственная схема школы, а не история**: настоящие ланисты подбирали типы асимметричными парами (мурмиллон против фракийца или гопломаха, ретиарий против секутора), универсального «камень-ножницы-бумага» с зеркалами не существовало. Экран планирования печатает эту оговорку прямо под правилом.

Школа делит один и тот же ростер из **пяти гладиаторов** (три калиброванных «ветерана» и два «скамеечных» специалиста, каждый — не строгое улучшение/ухудшение ветерана своего типа) на три серии подряд, и бой оставляет след: каждый проведённый бой изнашивает гладиатора по **ступеням состояния** (`fresh → bruised → wounded → broken`), которые определяют его стартовое HP следующего боя как долю максимума — `1.00 / 0.75 / 0.50` для `fresh/bruised/wounded`; `broken` не может выйти на бой вообще. Победа при остатке HP ≥25% стоит одну ступень, поражение или победа с остатком <25% — две. Гладиатор, не попавший в состав серии, **отдыхает** и восстанавливает одну ступень (отдых из `fresh` — no-op, восстановить сверх максимума нельзя). Если по износу для серии фактически годны меньше трёх гладиаторов, интерфейс планирования заранее предупреждает об этом, и оставшиеся слоты после подтверждения состава **форфейтятся** (засчитываются как поражение без боя) — сезон всё равно доигрывается и завершается итоговым экраном по всем трём сериям.

URL-параметр `?seed=<uint32>` воспроизводит весь сезон целиком — все три серии, состав противников и весь износ по ступеням: случайность полностью детерминирована для одинаковых назначений, сида (сезона и производных от него посерийных сидов) и числа тиков (см. «Детерминизм и сиды» ниже).

## Запуск

Нужны Node.js 22+ (или 20.19+) и npm.

```bash
npm install
npm run dev
```

Vite откроет приложение на `http://127.0.0.1:4173` и будет обновлять его без полной перезагрузки.

## Три типа гладиаторов

Каждый тип — не только другой набор чисел, а другой узнаваемый рисунок движения: разный радиус предпочитаемой дистанции, разная скорость сближения/отхода, разные типы атак и разное защитное действие. Все три специально движение-насыщенные (movement-rich) — они должны узнаваться по силуэту и ритму сближения/отхода ещё до того, как нанесён удар. Тип — это ещё и снаряжение, по которому боец опознаётся на арене: щит, шлем и оружие нарисованы так, чтобы читаться на том размере, на котором они реально отрисованы:

- **Murmillo** (например, Brutus) — большой изогнутый прямоугольный скутум, гладиус, шлем с широкими полями и гребнем, одна низкая окрея на левой ноге. Держит короткую дистанцию (1.2–1.7), не отступает вовсе (вес отхода — 0), атакует редко, но тяжело: пробный `heavy-shield-jab` (щитом, без возможности парировать) и вложенный `heavy-cleave`; защищается `heavy-guard` (блок щитом).
- **Retiarius** (например, Aquila) — сеть и трезубец, **ни щита, ни шлема**, только галерус на левом плече. Держит самую дальнюю предпочитаемую дистанцию из трёх (2.4–3.0) и отходит чаще всех, входит рывком: пробный `fast-slash` и вложенный `fast-burst-lunge` (рывок в упор), после которого следует вынужденный откат (`disengage`); защищается уклонением `fast-evade`.
- **Hoplomachus** (например, Nerva) — колющее копьё, маленькая круглая парма, высокие поножи на обеих ногах, шлем с полями без гребня. Держит дистанцию (2.1–2.8, атаки достают до 3.1 — самый длинный вылет в ростере: «measure», выжидающая стойка `hold-range`/`backstep`), колет издалека `technical-thrust`/`technical-driving-thrust`; защищается парированием `technical-parry`, и удачный парирующий обмен даёт вынужденную контратаку `technical-parry-counter`.

Историческая часть здесь — **снаряжение**; поведение (кто сближается, кто отдаёт дистанцию) — наша игровая трактовка этого снаряжения, а не реконструкция приёмов. Подробности и уровень достоверности по каждому элементу — `docs/reference/gladiator-equipment.md`.

На арене это не процедурный риг, а готовые модели: CC0-набор KayKit Adventurers из `assets/kaykit/`, собранный в `public/models/*.glb` скриптом `tools/blender/build_gladiators.py` (Blender 5.2, запускается как `npm run models:build`; рядом лежит `tools/inspect-glb.mjs` — не собирает, а печатает боны/анкоры/клипы уже собранного `.glb`, для проверки без открытия Blender). Мурмиллон — это Knight с `1H_Sword` и `Rectangle_Shield`; ретиарий — Barbarian с достроенными скриптом трезубцем и сетью (в паке их нет); гопломах — Rogue с достроенным скриптом копьём и пак-овым `Round_Shield`. Стоя все три ростом 2.0 игровых единицы (было 1.8 до Task 7b — поднято ради 130-пиксельного порога читаемости, см. `docs/superpowers/specs/2026-09-04-skinned-gladiators-design.md` §2.2). Анимация — клипы пака (`1H_Melee_Attack_Chop`, `Block` и т.д.) плюс один собственный, авторски выставленный клип `Spear_Drive` (выпад гопломаха копьём); какой клип и на какой фазе играть — решает `src/presentation/clipMapping.ts` по тику и фазе действия.

**Внутренние идентификаторы остаются `heavy`/`fast`/`technical`** (и вместе с ними `heavy-cleave` и прочие id действий) — исторические имена живут только в презентации (`src/presentation/gladiatorTypes.ts`), симуляция про них не знает. Причина не косметическая: `traceHash` сворачивает `JSON.stringify(event)` по каждому событию, а события несут в себе id действий, — переименование сломало бы замороженный `dc635911` без единого выигрыша для игрока.

## Приказы и темпераменты

Перед каждым боем серии игрок (и, зеркально, соперник) сражается под одним из трёх **приказов** (`DispositionId`): **Standard** — как обучен, без изменений; **Press** — выше шанс победы, но и выше шанс дорого за неё заплатить; **Guarded** — бережёт HP и износ ценой шанса на победу. Приказ выбирается на экране планирования серии (любой из трёх боёв) и между боями — но только для следующего непроведённого боя: уже отыгранный бой и бои дальше следующего в очереди недоступны для смены приказа и отвечают `order-locked`.

Начиная со второго испытания к тому же полю относятся и соперники: каждому противнику по контенту сезона назначен свой **темперамент** (тот же `DispositionId`, с отдельными подписями — **Steady** / **Aggressive** / **Cautious**) — первое испытание нарочно все `standard` (это и есть замороженная базовая серия); второе испытание — авторская строка `press`/`guarded`/`standard`; третье — `standard`/`press`/`standard` (третье испытание уже целиком расходует бюджет сложности на масштабирование характеристик соперников, поэтому его темпераменты подобраны не для дальнейшей эскалации, а ради разнообразия — и по замеру оказываются даже чуть легче нейтрального варианта (61.0% против 52.5% для сильнейшего состава), а не строго нейтральными по сложности; подробности и замеры в комментарии к `TEMPERAMENTS` в `src/content/season.ts`). Темперамент соперника меняет, насколько тяжело дастся бой, но не меняет, какой приказ для этого боя лучший — правильный приказ определяется тем, **с кем** боец дерётся (контр-треугольник типов), а не тем, как настроен противник; сам мотив приказа остаётся сообразным на протяжении сезона.

Инвариант: приказ — это только веса решений в `src/simulation/disposition.ts`, наложенные поверх существующего шва `combatDecision.ts`; `standard` байт-идентичен прежнему поведению (не устанавливает никакого нового ключа состояния), поэтому все замороженные хэши боя не изменились. Детерминизм не нарушен: сезон по-прежнему полностью воспроизводится из `(seed, составы, приказы)`.

## Детерминизм и сиды

Вся симуляция боя — фиксированный тик (`TICKS_PER_SECOND`, `src/simulation/battle.ts`), без обращения к `Date.now()`, `Math.random()` или к тригонометрии/трансцендентным функциям времени выполнения (`architecture.test.ts` проверяет это статически). Одинаковые входные данные (состав, сид, число тиков) всегда дают одинаковый след событий и один и тот же контрольный хэш следа (`traceHash`/`formatTraceHash`, `src/simulation/random.ts`).

Это гарантировано не только внутри одного рантайма (Node/Vitest), но и между Node и браузерным Chromium — `tests/combat-visuals.spec.ts` напрямую импортирует тот же модуль симуляции через dev-сервер Vite и сверяет итоговый хэш с тем же литералом, который заморожен в `battle.test.ts` (`dc635911`). Это ядро специально заморожено (Task 13): любое несовпадающее с фиксированными значениями изменение в `src/simulation/**`/`src/content/**` — повод чинить тест, а не подгонять литерал.

Интерполяция кадра (альфа между предыдущим и текущим тиком, для плавности при рендере) — величина чисто презентационная: `renderActiveBattleAtAlpha` меняет то, что нарисовано, но никогда не двигает `currentTick` вперёд и не влияет на симуляцию.

## Runtime: пауза, скорость, звук

Пауза и скорость `×1/×2/×4` влияют только на runtime (сколько фиксированных тиков проходит за единицу реального времени) и не меняют состояние симуляции — при паузе `advanceTicks`/тесты по-прежнему могут продвигать бой вручную, а `×2`/`×4` просто выполняют по 2/4 тика симуляции за один кадр рендера вместо одного.

Звук — событийный (`src/presentation/CombatAudio.ts`), включается по первому реальному пользовательскому жесту (клик `Confirm lineup` или явный клик `Sound on`) — это требование браузерного autoplay-policy. `Sound off` мьютит воспроизведение, не касаясь симуляции или серии. Провал инициализации `AudioContext` (или его отсутствие) не должен останавливать или портить бой — звук деградирует тихо.

Потеря WebGL-контекста (`webglcontextlost`) заменяет канвас на текстовый fallback и не прерывает и не восстанавливает симуляцию/серию — раунды продолжают идти, `Start next bout` продолжает работать, просто без 3D-рендера до конца сессии.

## Камера: рамка по группе

`ArenaCamera` кадрирует пару по **групповому экстенту** — расстоянию между бойцами плюс радиусы их снаряжения с запасом, — и переводит его в дистанцию камеры кусочной функцией `extentToDistance`:

- **плоская область**, экстент ≤ `BAND_HIGH_EXTENT` (7.53123 — верхняя кромка тактического коридора у самой широкой пары, выведенная из максимального вылета атаки 3.1 и самого широкого радиуса снаряжения; было 6.07242 до Task 7, где скиннинг гладиаторов пересчитал радиусы снаряжения, и 7.08811 до Task 7b, где гладиаторов подняли с 1.8 до 2.0 единиц роста ради 130-пиксельного порога читаемости): весь коридор снимается ровно с `FLAT_DISTANCE = 8.81`;
- **разъезд**, выше кромки: smoothstep до `CAMERA_MAX_DISTANCE = 18` на протяжении `EASE_WIDTH_EXTENT = 7.0` экстента. Smoothstep, а не прямая: производная нулевая на обоих концах, поэтому камера уходит из плоской области и приходит в кламп без рывка (C1).

`ArenaView`'s `CAMERA_MIN_DISTANCE` равен самому `FLAT_DISTANCE` — именно затем, чтобы нижний кламп не мог перебить плоскую область.

Это заменило прежнее отображение `clamp(8.5 + 0.8 × extent, 11, 18)`, у которого нижний кламп `11` держал бойцов нечитаемо мелкими и делал типы неотличимыми — но два числа за этим стоят разные и не взаимозаменяемые. Инструментальный замер (скриптом `measure-framing.ts`, удалён вместе с остальными инструментами слайсов; см. историю git) даёт типичному внутрикоридорному размену **93–111 px роста тела** (без снаряжения) на 518-пиксельном канвасе — это реальная высота 3D-канваса внутри страницы, а не весь вьюпорт — и **68 px в худшем случае**. Более ранняя ручная прикидка разработчика (проверка от 2026-08-19, `docs/reviews/2026-08-16-readable-deep-combat-human-review.md`, §3) оценивала на глаз **50–90 px** — но это весь силуэт бойца целиком, снаряжение включено, по полнокадровым скриншотам 1280×820. Числа не противоречат друг другу: они меряют разные величины (рост тела на канвасе против всего силуэта на кадре) разными методами (скрипт против глаза) — но указывают на один и тот же дефект. Обе константы (`8.81`, `7.0`) не назначены на глаз, а **подобраны развёрткой**: тот же скрипт с флагом `--sweep` переигрывал 7 189 пар-кандидатов `(FLAT_DISTANCE, EASE_WIDTH_EXTENT)` на 46 647 записанных тиках — все девять пар бойцов на трёх вьюпортах, — а окончательное значение выбрано прямым замером в браузере (почему не по развёртке — в комментарии к `FLAT_DISTANCE`). Что это гарантирует, проверяет `tests/legibility.spec.ts`: на 1280×820 рост тела держится выше 130 px на 92-м процентиле «в-коридорных» тиков. За 5%-ю рамку канваса на всех трёх вьюпортах (1280×820 / 1024×768 / 820×640) разрешено выходить только длинному ручному снаряжению на вылете и броске — древку копья гопломаха, трезубцу ретиария и (поправка 2026-09-05) его же сети: она держится на вытянутой руке и бросается точно так же, как трезубец, в паре с которым носится. Всё остальное (тело, шлем, щит, галерус, поножи и гладиус мурмиллона — это не древковое оружие) обязано укладываться в рамку на каждом тике всех девяти пар на всех трёх вьюпортах, кроме одного именованного исключения: пара «05 aquila vs cassius» (ретиарий против гопломаха) на 1024×768, где сеть выходит за рамку не более чем на 12 тиков из прогона и не глубже чем на 18 px сверх рамки (`KNOWN_SAFE_AREA_DEVIATIONS` в `tests/legibility.spec.ts`) — это зафиксированное измеренное отклонение, а не ослабление правила: тест по-прежнему падает, если оно углубится или расползётся на другую пару.

Зоны нечувствительности взгляда и рыскания, а также постоянные времени демпфирования этим слайсом не менялись.

## Архитектура: encounter vs duel-адаптер

- `src/simulation/encounter.ts` — общее ядро столкновения: коллекции по `CombatantId` (не по «стороне»), пространственный хэш, движение, решения, фазы действий, защита, контакт, урон, наступление стагера и завершение. Рассчитано на произвольное число участников с враждебностью — не только на дуэль 1×1.
- `src/simulation/battle.ts` — тонкий адаптер поверх `encounter.ts`, который отображает ровно двух участников (`home`/`away`) на текущий 1×1 UI серии школы: это единственное место, которое всё ещё знает про «домашнего» и «противника» как игровое понятие.
- `src/simulation/series.ts` — три боя одной серии, назначение состава, межбоевые интерстишлы, итог серии, форфейт пустых слотов после подтверждения состава. Его собственная функция `rematch` (переигровка той же серии заново) сейчас не вызывается из рантайма вообще: она осталась самостоятельным примитивом уровня серии, покрытым только собственными тестами. На экране итога серии кнопка называется `Continue` и вызывает сезонную `continueSeason` (см. ниже).
- `src/simulation/condition.ts` — **владелец ступеней состояния**: сам ладдер `fresh → bruised → wounded → broken`, доли стартового HP (`1.00 / 0.75 / 0.50`), правило износа и правило отдыха. Пороги живут здесь и больше нигде.
- `src/simulation/season.ts` — состояние сезона поверх `series.ts`: **применяет** переходы из `condition.ts` к ростеру (износ дравшимся, отдых отдыхавшим), хранит три `ChallengeDefinition` (масштабированные по серии противники), форфейт-правило на уровне сезона и переходы `season-board → series → season-summary`. Презентация (`SeasonView.ts`/`SeriesView.ts`) ни ладдер, ни его применение не вычисляет — только форматирует готовое `SeasonState`.
- `src/presentation/` — Three.js-сцена (`ArenaView.ts`), скиннованный риг из готовых `.glb` и покадровый проигрыватель клипов (`SkinnedFighter.ts`, `FighterAnimator.ts`, `clipMapping.ts`, `fighterModelContract.ts`), камера с рамкой по группе (`ArenaCamera.ts`), звук (`CombatAudio.ts`), экран сезона и итоговая сводка (`SeasonView.ts`), экран планирования/боя одной серии (`SeriesView.ts`). Презентация не содержит игровых правил: она только читает `SeasonState`/`BattleState`/`EncounterEvent` и форматирует/интерполирует.
- `src/main.ts` — runtime-loop (тик-аккумулятор, привязка HTML UI, dev-only test API `window.__GLADIATOR_TEST__`).
- `tests/` — Playwright smoke/визуальные тесты и эталонные screenshot-baselines.

Сегодняшний игровой UI — **строго 1×1**: серия из трёх дуэлей, а не свободный масс-бой. `encounter.ts`'s способность вести до 100 участников (см. ниже) существует уже сейчас, но не выставлена ни в какой играбельный режим.

## 100-комбатантный FFA-фикстур — не прототип читаемого масс-боя

`src/testSupport/combatFixtures.ts`'s `createHundredCombatantFfa` и связанные с ней тесты в `encounterCapacity.test.ts` доказывают, что ядро `encounter.ts` структурно выдерживает до 100 участников без деградации инвариантов (уникальные ID, ограниченные списки реакций, канонические пары пространственного хэша и т.д.) — это **детерминированный/структурный регрессионный фикстур для ядра**, ничего больше.

Он **не** является прототипом читаемого масс-боя. Управление зонами вовлечения (engagement slots), защита от «свалки» (dogpile prevention), построения и групповая тактика — не реализованы и остаются будущей работой отдельного масс-боевого слоя поверх того же ядра.

## Будущие skill/perks

Ядро решений (`src/simulation/combatDecision.ts`) специально оставляет для будущего `combatSkill`/perks отдельный, устойчивый шов: построение контекста, фильтрация легальных действий, взвешенный выбор и исполнение действия — разделены. Будущий скилл/перк (например, `Patient` меняет вес `committed`-тегированных действий, `Counterfighter` — вес `counter`, `Fleet-footed` — защитное движение) может изменять **скоринг решений и параметры протегированных действий в симуляции**, но не имеет права входить в код позы или рендерера — presentation остаётся правило-свободной (rule-free) даже после того, как появится прогрессия.

## Проверки

```bash
npm test                     # unit-тесты simulation/presentation (Vitest)
npm run test:watch           # unit-тесты в watch-режиме
npm run test:e2e             # Playwright: product-flow, детерминизм, ключевые позы, screenshot baselines
npm run test:e2e:update      # принять намеренное изменение screenshot baseline (весь набор)
npm run build                # TypeScript + production build
npm run check                # полная официальная последовательность: test && build && test:e2e
npm run models:build         # пересобрать public/models/*.glb из assets/kaykit (нужен Blender 5.2)
npm run benchmark:encounter  # информационный (не CI-gate) замер 100-комбатантного FFA
```

Перед первым e2e-запуском может понадобиться `npx playwright install chromium`.

Обновлять только конкретные намеренные baseline-скриншоты (не весь набор разом):

```bash
npx playwright test tests/combat-visuals.spec.ts --update-snapshots
```

После обновления обязательно посмотреть каждый diff глазами — читаемый силуэт, интервал между бойцами, видимые anticipation/contact/recovery, стабильная камера, корректные подписи статов; не принимать попутные изменения planning/interstitial/summary-экранов, если они не были целью правки.

И **смотреть глазами не только на упавшие baseline'ы**. `--update-snapshots` переписывает только то, что само измерило как изменившееся, а зелёный WebGL-снимок ещё не значит совпадающий: при `threshold: 0.2` гладкий градиент арены и большое тёмное поле вокруг канваса меняются слишком мало на пиксель, чтобы попасть в счёт, поэтому кадр может показывать других бойцов другого размера и всё равно уложиться в 4%. Так и вышло в слайсе 2026-08-23: `heavy-cleave`, `fast-burst`, `technical-parry` и `combat-outcomes` прошли гейт против заведомо устаревших эталонов. Лечится это не подкруткой порога (2.5% межмашинного разброса WebGL меряно и ниже 4% опускаться нельзя), а тем, что при намеренном изменении рендера эталоны пересматриваются целиком — при необходимости удалением файла, чтобы `--update-snapshots` пересоздал его как отсутствующий.

Самое наглядное свидетельство, что ratio — не тот инструмент для арены: `season-board.png` в том же прогоне сдвинулся всего на **0.66%** (6 912 px) — этого не хватило бы даже на общий 4%-й порог, и он был пойман исключительно собственным ужесточением `maxDiffPixelRatio: 0.002` (`tests/season.spec.ts:405`), а не порогом WebGL-снимков.

`npm run benchmark:encounter` печатает одну строку JSON с метриками (тики, число событий, `millisecondsPerTick` и т.д.) для 100-комбатантного FFA — это чисто информационный замер, время выполнения не является порогом ни в одном тесте/CI.

## Dev-only отладка

Весь `window.__GLADIATOR_TEST__` — включая базовый командный/инспекционный API, а не только расширения ниже — существует только в dev-режиме (`import.meta.env.DEV`; полностью вырезается из production-сборки статически, проверено сборкой + поиском по бандлу). `?snapshot` (стартует сезон на паузе, для стабильного первого кадра в Playwright-фикстурах) читается тем же способом и тоже не действует в production. `tests/global-setup.ts` всегда поднимает dev-сервер Vite, поэтому продакшен-сборке ничего из этого не нужно.

Базовый API теперь работает на уровне сезона, не одной серии — старые `getState()`/`rematch()` удалены вместе с автомостом мимо экрана сезона (см. `simulation/season.ts`):

- `getSeasonState()` / `getActiveSeriesState()` — снимок всего `SeasonState` (ростер со ступенями состояния, испытания, счёт, записи по сериям) и, если серия сейчас открыта, снимок её собственного `SeriesState`; `null`, когда открыт экран сезона/итога.
- `startNextSeries()` — то же самое действие, что и клик по кнопке `Start series N` на экране сезона: открывает планирование следующей серии.
- `assign(fighterId, boutIndex)` / `unassign(boutIndex)` / `confirm()` — планирование состава текущей серии; `assign` на гладиатора со ступенью `broken` возвращает `{ ok: false, reason: 'fighter-unavailable' }` до обращения к самой серии.
- `setBoutOrder(boutIndex, order)` — выставляет приказ (`standard`/`press`/`guarded`) для указанного боя серии; допустимо на планировании (любой бой) и между боями (только следующий непроведённый), иначе возвращает `{ ok: false, reason: 'order-locked' }`. Индекс вне диапазона `0..2` и неизвестный идентификатор приказа — это ошибки программиста, а не отказ команды: они бросают исключение, как и обращение к неизвестному бойцу.
- `advanceTicks(ticks)` / `startNextBout()` — продвижение боя и переход к следующему бою серии, как и раньше.
- `continueSeason()` — то же действие, что и клик по кнопке `Continue` на экране итога одной серии: закрывает только что законченную серию (износ ростера, её `SeriesRecord`, счёт сезона) и возвращает на экран сезона (или на итог сезона, если серия была третьей).
- `rematchSeason()` — кнопка `Rematch season` на итоговом экране: сбрасывает ростер и записи и начинает сезон заново с тем же сидом.
- `getActiveBattleTraceHash()`, `getActiveCombatantPositions()`, `getRenderDebugState()` — без изменений.

Также в dev-режиме доступны:

- `window.__GLADIATOR_TEST__.renderActiveBattleAtAlpha(alpha)` / `.getArenaDebugSnapshot()` — рендер на произвольной альфе и числовой снапшот сцены (позиции корней ригов, конечность всех joint-трансформов, активные ID вспышек контакта, состояние камеры, курсор событий) для тестов без модификации самой симуляции.
- `window.__GLADIATOR_TEST__.getAudioEventCursor()` — читает собственный курсор событий `CombatAudio`, независимо от `?audioDebug=1`.
- `window.__GLADIATOR_TEST__.forcePresentationThrowOnce()` — форсирует однократный throw в презентационном шаге следующего кадра, чтобы тест мог проверить, что такой сбой отключает только рендер (`getRenderDebugState().presentationDisabled`), а не продвижение тиков симуляции.
- `?audioDebug=1` — панель из девяти кнопок, по одной на каждый `CombatCue`, воспроизводящих звук напрямую через реальный бэкенд, не запуская бой. `window.__GLADIATOR_TEST__.getAudioDebugLog()` возвращает список уже проигранных cue — для тестов без реального аудио-железа.

`?audioDebug=1` в production ничего не показывает и не создаёт debug test API (как и весь остальной test API выше).

## Human review

Числовые/структурные проверки (частота попаданий/блоков, заморозка ключевых поз на конкретных тиках, кросс-runtime хэш, screenshot-baselines) — необходимое, но не достаточное условие приёмки читаемости боя. Финальная приёмка требует **человеческого визуального/аудио-ревью** минимум двух человек, не писавших боевую логику (design.md, раздел «Human review gate»; шаблон отчёта — `docs/reviews/2026-08-16-readable-deep-combat-human-review.md`). Это ревью нельзя заменить текстовой моделью и нельзя засчитать из автоматической/модельной оценки — критерий: `>= 75%` верно опознанных выигрышных (committed) обменов на ревьюера, опознание всех трёх типов по одному клипу каждый, и правдоподобное объяснение победителя на трёх показательных клипах.

## Дальнейший roadmap

Ядро боя, риг, поза, камера и опциональный звук уже реализованы поверх зафиксированной (frozen) симуляции. Дальнейшая работа — за пределами этого слайса:

1. Прогрессия: опыт за победы, `combatSkill`/perks поверх существующего шва в `combatDecision.ts`.
2. Выбор испытания/кампания.
3. Масс-боевой слой поверх `encounter.ts` (зоны вовлечения, защита от свалки, построения, групповая тактика, масс-UI/камера).
4. Импортированные модели: сделано (KayKit + Blender-пайплайн); следующий шаг — свои клипы под каждый тип.
5. Performance-бюджеты для слабого десктопа и мобильных.

Правило проекта: playable slice важнее идеальной архитектуры, но simulation остаётся независимой от renderer-а, а renderer — правило-свободным (rule-free).
